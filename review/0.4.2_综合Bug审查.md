## 二、详细审查意见

### BUG-042-01：处理中新增的 TIFF 会生成 ROI，但被 ImageJ 静默漏测

**严重程度：高**

#### 涉及位置

- `src/worm_roi_gui.py:1508-1509`：GUI 预检时枚举当前 TIFF。
- `src/worm_roi_gui.py:1667-1680`：调用批处理时没有传入 `input_paths`。
- `src/worm_roi_gui.py:1693`：桥接完成清单固定使用预检时的 `source_names`。
- `src/batch_worm_roi.py:1186-1190`：后台线程再次扫描输入目录。
- `src/worm_roi_gui.py:1949-1957`：完成通知只从预检时的 `source_names` 生成。
- `plugin_src/Auto_Worm_ROI.java:644-650`：Java 只测量完成清单中出现的文件。

#### 触发条件

1. 用户点击“开始处理”；
2. GUI 完成目录预检并记录当时的 TIFF 文件名；
3. 在后台线程再次扫描目录之前，采集软件、同步软件或复制操作加入一张新的 TIFF；
4. 后台批处理重新扫描目录，发现并正常处理这张新图。

#### 实际结果

- Python 会为新图生成 `*_RoiSet.zip`、`*_QC.png` 和 `batch_summary.csv` 成功行；
- 新图不在 GUI 预检时记录的 `source_names` 中；
- GUI 写出的 `ok_b64` 不包含新图；
- Java 看到非空完成清单后，以清单为准，静默跳过新图；
- 同批其他图可以正常测量，因此整批仍会显示“测量完成”，没有任何错误指出新图缺少测量表。

这会形成一种尤其危险的状态：ROI 和 QC 图都存在，批处理汇总也显示成功，但荧光测量缺失。

#### 修复建议

GUI 应把完成预检的同一份文件快照传给后台：

```python
batch_kwargs["input_paths"] = [str(path) for path in sorted_tiffs]
```

这样预检、实际处理、失败列表和桥接完成清单都基于同一批文件。建议增加一个回归测试：在 GUI 首次枚举后向目录加入新 TIFF，断言本批既不处理也不通知该新文件。

### BUG-042-02：陈旧测量表识别采用子串匹配，可能误删用户 CSV

**严重程度：高**

#### 涉及位置

- `plugin_src/Auto_Worm_ROI.java:582-593`：`removeStaleCombinedTable`。
- `plugin_src/Auto_Worm_ROI.java:612-624`：`removeStaleImageTable`。

#### 根因

代码声称通过两个列名识别本程序写出的表，但实际实现是：

```java
header.contains("CTCF") && header.contains("MeasurementBackend")
```

这是子串匹配，不是 CSV 完整列名匹配。例如以下表头也会通过：

```text
Image,RawCTCFValue,MeasurementBackendNotes,Comment
```

如果该文件恰好位于：

```text
measurements/ImageJ_measurements_all.csv
```

或使用某张图对应的 `<stem>_measurements.csv` 文件名，插件会在本轮测量前直接删除它。

#### 影响

- 输出目录允许由用户自行选择，不保证只含本程序生成的文件；
- 代码本身也明确承认同名文件可能属于实验人员，因此才设计了删除前识别；
- 当前识别方式没有真正实现这一保护，存在不可恢复的数据删除风险。

#### 修复建议

按 CSV 字段拆分首行，仅在字段集合中存在完整的 `CTCF` 与 `MeasurementBackend` 两列时删除。至少应避免裸 `String.contains`。

建议为合并表和单图表各增加两类测试：

1. 完整列名存在时确实删除；
2. 只有 `RawCTCFValue` / `MeasurementBackendNotes` 等包含子串的列时绝不删除。

### BUG-042-03：全部图像失败时，ImageJ 收不到真正的失败原因

**严重程度：中**

#### 涉及位置

- `src/batch_worm_roi.py:1346-1364`：单图异常被捕获，整批继续。
- `src/worm_roi_gui.py:1858-1862`：只要线程正常返回，就发送 `status=complete`。
- `plugin_src/Auto_Worm_ROI.java:121-140`：先尝试测量，且只在 `measured == true` 时显示桥接消息。
- `plugin_src/Auto_Worm_ROI.java:715-718`：成功数为 0 时抛出“没有可测量 ROI”的异常。

#### 触发条件

批内每一张图都在 `process_image` 中失败。由于单图异常是受支持的容错路径，`run_gui_batch` 最终仍正常返回，GUI 因而发送：

```text
status=complete
ok_count=0
message_b64=<每张失败图的真实原因>
```

#### 实际结果

Java 收到空完成清单后仍调用 `measureOutputFolder`。它测不到任何图，抛出“输出目录中没有可测量的 ROI ZIP”。处理器中的真实失败消息只有在 `measured` 为真时才显示，因此被吞掉。

用户在 ImageJ 端看到的是测量阶段错误，而不是实际发生的分割/后处理错误。源码中 `_failure_message` 的注释明确指出 ImageJ 端没有其他途径获知失败原因，当前实现却恰好在最需要它的“全部失败”分支不显示。

#### 修复建议

当通知明确携带 `ok_count=0` 时：

- 不进入测量流程；
- 直接显示 `message_b64` 中的失败列表；
- 将该通知视为已处理，但不要声称完成了 ImageJ 测量。

另外，即使 `measureOutputFolder` 自身失败，也应把桥接消息附在测量错误后面，避免丢失上游诊断信息。

### BUG-042-04：背景搜索会把存在合格空白区域的图误判为失败

**严重程度：中**

#### 涉及位置

- `src/batch_worm_roi.py:760-775`：`_largest_clear_rectangle`。
- `src/batch_worm_roi.py:813-823`：四个候选条带的背景搜索。

#### 根因

函数名与注释称它查找“区域内面积最大的全空矩形”，但算法只接受在整个候选条带高度内完全没有障碍的列：

```python
for column_start, column_end in _clear_runs(~region.any(axis=0)):
```

某一列只要有一个虫体或排除区像素，整列就不会参与任何候选矩形。它无法找到位于障碍物上方或下方的空矩形，因此不是真正的一般最大空矩形算法。

#### 最小复现结果

使用生产函数构造 100×100 掩膜，在候选条带中放置很薄的横向排除区域。候选条带内仍明确存在 680 像素的完全干净矩形，但运行结果为：

```text
production_background_is_none = True
known_clean_top_rectangle_area = 680
top_probe = None
```

680 像素明显高于当前 `BACKGROUND_MIN_AREA_PIXELS = 200`，仍被判为没有背景。

#### 影响

当虫体靠近多侧边缘、剩余候选条带中横穿人工排除区时，程序可能错误报告：

```text
找不到干净背景区域
```

图像随后被记为失败，即使实际上仍有面积足够且完全干净的矩形背景。

#### 修复建议

采用标准的“逐行直方图最大矩形”算法；或者保留当前快速路径，在它找不到足够面积时再运行正确但稍慢的回退搜索。

回归测试至少应覆盖：

- 候选条带中间横穿一条排除带，但其上方仍有合格矩形；
- 障碍只占每列少量像素；
- 返回的背景 mask 与导出 polygon 逐像素一致。

### BUG-042-05：发布检查不能阻止陈旧 Java JAR 进入发行包

**严重程度：中**

#### 涉及位置

- `make_release.py:325-328`：只检查 JAR 和 EXE 是否存在。
- `make_release.py:338-359`：源码一致性检查只针对 EXE 中的 Python 模块。
- `make_release.py:374-385`：检查通过后直接收集现有 JAR 并打包。

#### 问题

修改 `plugin_src/Auto_Worm_ROI.java` 或 `Auto_Worm_Annotations.java` 后，如果开发者忘记重新运行 Java 构建：

- `dist/Auto_Worm_ROI.jar` 仍然存在；
- Python EXE 仍可与 `src/` 完全一致；
- `make_release.py` 所有强制检查都会通过；
- 最终 ZIP 会包含旧 JAR。

桥接协议和输出目录名同时存在于 Python 与 Java 两侧。若只更新一边，可能出现“程序正常启动但什么都不测”的静默失效，因此仅靠人工清单不足以保证发布安全。

#### 当前产物说明

本轮审查没有发现当前 JAR 已陈旧：Java 源码可重新编译，两套 Java 测试通过，现有 JAR 时间也晚于源码。本条是发布工具允许未来错误产物通过的缺口。

#### 修复建议

可选方案：

1. `make_release.py` 调用 `javac --release 8` 在临时目录现场编译，并逐个比较 JAR 内 `.class`；
2. 构建时生成 Java 源码清单哈希，发布时强制比对；
3. 最简单但成本较高的方案是发布脚本始终先执行完整构建。

应增加一个测试：临时修改 Java 字符串但保留旧 JAR，断言发布检查拒绝继续。

### BUG-042-06：标注插件会静默丢弃类型错误的 ROI，却报告保存成功

**严重程度：低**

#### 涉及位置

- `plugin_src/Auto_Worm_Annotations.java:30-38`：只按名称前缀分类。
- `plugin_src/Auto_Worm_Annotations.java:43-45`：成功提示使用分类列表长度。
- `plugin_src/Auto_Worm_Annotations.java:63-72`：非 `Line` 的 `head_` ROI 被静默跳过。
- `plugin_src/Auto_Worm_Annotations.java:82-97`：不满足面积/点数要求的 ROI 被静默跳过。

#### 示例

用户把一个面积 ROI 命名为 `head_1`，并同时存在一项有效的其他类型标注：

- 分类阶段把它加入 `heads`；
- JSON 序列化阶段发现它不是 `Line`，直接 `continue`；
- 成功弹窗仍按 `heads.size()` 报告“头向 1”；
- 实际 JSON 中 `arrows` 是空数组。

排除区使用非面积 ROI、边界线点数不足时也有类似问题。

#### 影响

用户会相信标注已经写入，实际处理时该标注不存在。部分圈画模式稍后可能通过箭头数量检查发现问题，但普通手工拆分可能只是静默不生效。

#### 修复建议

在写文件前对所有带受管前缀的 ROI 做类型与点数校验：

- `head_` 必须是有效直线/箭头；
- `boundary_` 必须至少有两个有效点；
- `exclude_` 必须是有效面积 ROI。

发现无效项时拒绝保存并列出 ROI 名称。成功提示应使用实际序列化数量，而不是分类前列表长度。
