## 2. P1 —— 会污染数据或锁死程序

### P1-1（GPT）单图测量表保存失败，该图的行仍留在合并表

- 位置：`plugin_src/Auto_Worm_ROI.java:608-610`（`measureWithImageJ` 追加 combined 的时机）、
  `plugin_src/Auto_Worm_ROI.java:645-670`
- 触发：某图测量完成但 `<图名>_measurements.csv` 写不进去（同名目录占位 / 文件被锁 /
  写入错误），且同批后面至少还有一张能正常保存。
- 原因：`measureWithImageJ` 返回**之前**就 `appendMeasurement(combined, …)` 了每一行；
  `one.saveAs` 的失败发生在这之后，外层 catch 只做 `skipped++`，没有把行撤回来。
  只要后面有一张成功，`combined.saveAs` 仍会写出。
- 证据（GPT 对发布 jar 的复现）：日志写 `aaa_bad.tif 无法测量，已跳过`、
  `aaa_bad_measurements.csv` 未生成，但 `ImageJ_measurements_all.csv` **同时含
  `aaa_bad.tif` 和 `bbb_good.tif`**。
- 危害：日志、单图表、合并表三者互相矛盾；合并表里出现了日志明说"已跳过"的图。
- 建议：先构造单图 `ResultsTable`、**可靠保存之后**再追加到 combined；两张表都改成
  「临时文件写完 + 原子替换」。
- Claude 复核：读码确认成立。**这是 Claude 那一轮漏掉的**——`Analyzer` 对照从未让保存失败过。

### P1-2（Claude）离线校验工具的光栅化约定没跟上 0.4.1 的半像素修复

- 位置：`src/inspect_roi_dataset.py:112-115`（`polygon_mask`），消费点 `:142`、`:149-167`
- 原因：`ImageDraw.Draw(mask).polygon(points, outline=1, fill=1)` 是**按像素格子填充**，
  等价于 AGENT.md 里记录已被 0.4.1 修掉的 `cv2.fillPoly` 约定（AGENT.md §9：
  「ImageJ 以像素中心为取样点、`cv2` 以像素坐标为取样点」，同一矩形 ImageJ 6188 / Python 6360）。
  导出侧改了，这条消费侧没改。
- 证据（Claude 实测，用项目自己的 `instance_contours` 产出的顶点）：

  ```
  worm mask px        : 3361
  ImageJ convention   : 3361     <- 像素中心取样，与掩膜逐像素相同（0.4.1 的承诺）
  PIL polygon_mask    : 3568
  area_scale reported : 0.9420   <- 应为 1.0000
  ```

  小方块上规律是 `(n+1)²`：1×1 掩膜光栅成 4、2×2 → 9、3×3 → 16、10×10 → 121。
  **不是只对半像素顶点成立**：手工在 ImageJ 画的整数顶点多边形同样偏，
  同一只虫 ImageJ 数 4200 px、PIL 数 4331。
- 危害：这个工具的用途正是"证明 ROI 与掩膜一致"，它在**完全正确的数据**上系统性报出
  ~6% 偏差；`Mean`/`RawIntDen` 的 MAPE 被多出来的背景环抬高；相距 1 px 以内的两个 ROI
  会被算成重叠。
- 波及面：`polygon_mask` 还被 `src/prepare_segmentation_dataset.py:110` 与
  `src/prepare_boundary_finetune_dataset.py:101` 用来造训练掩膜。但 AGENT.md §9 已写明这两个
  工具服务的是人工 ROI 集（`RoiSet_*.zip`），自动输出 `<stem>_RoiSet.zip` 不在其 glob 内，
  **当前出货流程碰不到**；影响是"离线校验会骗人" + "将来拿自动输出做数据集会踩"。
- 建议：改用与项目其余部分一致的像素中心约定光栅化，并加一条「掩膜像素数 == 轮廓像素中心
  计数」的断言，防止再次漂移。

### P1-3（Claude）GBK 编码的 `batch_summary.csv` 让程序启动即崩且自我锁死

- 位置：`src/worm_roi_gui.py:2450`（`_load_qc_status_summary` 的 `except`）
- 原因：只捕获 `(OSError, csv.Error)`，而 `UnicodeDecodeError` 是 `ValueError`；
  解码是惰性发生在 `for row in csv.DictReader(handle)` 里。
  对照 `src/batch_worm_roi.py:310` 同一读取写的是
  `except (OSError, UnicodeDecodeError, csv.Error)` ——**是漏写，不是有意**。
- 证据（Claude 直接调用该函数喂 GBK 文件）：

  ```
  ESCAPED: UnicodeDecodeError 'utf-8' codec can't decode byte 0xb3 in position 36
  ```

- 触发路径很日常：README 让用户读 `batch_summary.csv`，Excel 在 zh-CN 机器上打开再保存
  就写成 GBK；该文件夹路径是持久化的（`_load_folder` / `_add_recent` / `_choose_output_path`
  都会存），于是**每次启动都炸**、写 `gui_crash.log`、弹「界面启动失败」，用户必须自己找到
  那个 CSV 改名或删掉才能再用。
- 建议：`except (OSError, UnicodeDecodeError, csv.Error)`，与批处理模块对齐
  （或直接复用同一读取函数，别再有两份）。

### P1-4（Claude）`_poll_events` 的 `after` 写在 `try` 外面，事件泵一死窗口就关不掉

- 位置：`src/worm_roi_gui.py:1754-1781`（`after` 在 1781，位于 `try` 之外）
- 原因：`_poll_events` 只在两处被重新挂上——393（启动）和它自己的尾行 1781。
  队列排空期间任何非 `queue.Empty` 的异常都会跳过 1781，链条再也不续。
- 证据：读码确认重挂点只有这两处；`_processing_finished`（1786 起）里会调
  `_scan_qc_images`，而 P1-3 的解码异常正好能在该路径抛出——**两条会连锁**：
  批次失败 → `_processing_finished(-1)` → 读到上一轮被 Excel 存成 GBK 的汇总表 → 泵死。
- 危害：窗口看着还活着但完全没反应（打包版无 stderr，Tk 默认的
  `report_callback_exception` 输出无处可去），`_on_close`（2703）又把关闭委托给这个已死的泵，
  于是 **✕ 彻底失效，只能任务管理器杀进程**；若是由插件拉起的 GUI，
  等待通知/进程退出的 Fiji 侧会一起卡住。
- 建议：把 `after` 挪进 `try`（或用 `finally` 兜底重挂），并给
  `report_callback_exception` 装一个把异常写进终端面板的处理器。

## 4. P3 —— 脏、矛盾或难恢复

### P3-9（Claude）文件夹名里带 `[` `]` 会让整批被拒

- 位置：`src/batch_worm_roi.py:1059`（`glob.glob(os.path.join(input_folder, pattern))`）
- 原因：路径未转义，`glob` 把 `[batch2]` 当字符集。
- 证据（实测）：`os.listdir` 看得到图，四个 pattern（`*.tif`/`*.tiff`/`*.TIF`/`*.TIFF`）
  全部零命中，抛 `FileNotFoundError("No TIFF images found in: " + input_folder)`。
  GUI 用 `iterdir()` 列目录，**界面会把图显示出来然后拒绝运行**，信息完全对不上。
- 建议：`glob.escape(input_folder)`，一行。

### P3-10（GPT）已保存的空间校准被误判为「窗口与磁盘不同」

- 位置：`plugin_src/Auto_Worm_ROI.java:353-356`
- 原因：`pixelWidth` / `pixelHeight` / `pixelDepth` 用 double **精确不等**比较；
  TIFF 保存空间校准会发生有限精度序列化，窗口仍保留写入前的 double，重读得到量化值。
- 证据（GPT 对发布 jar 的复现）：窗口 `pixelHeight = 0.123456789`，保存并重读后
  `= 0.1234567901234568`，`window.changes = false`，仍报「空间校准不同」；
  `1/3`、`0.123456789012345` 及真实样例附近的 `1.3810685880092863` 同样复现。
- 危害：**不影响数值**（`calibrationDifference` 只写日志），只造成反复误提示，
  用户只能一直点「确定」。
- 建议：空间尺度用与 TIFF 序列化精度相称的相对/绝对容差；
  `pixelDepth` 对当前单页二维面积、荧光、CTCF 没有影响，不应单独触发提示；
  真正不同的单位与明显尺度差仍应提示。

### P3-11（Claude）`_split_qc.csv` 缺陈旧清理分支

### P3-12（Claude）退出请求被吞 / 桥接残留永久挡住「开始」

### P3-13（Claude）`ok_b64` 的「精确比较」契约两头不一致

## 6. 一条被排除的「缺陷」（重要）

几何审查最初把 `worm_shape_refiner.py:783-804` 的重叠归属报为缺陷，理由是
`best_distance` 从 `inf` 起手、判据 `best_distance >= 0` 使得
"后到的候选永远抢不走已归属像素，编号小者恒赢"。

**逐行复核后确认是误读。** 那个 `>= 0` 的语义是「尚未被**原属主**锁定」，
